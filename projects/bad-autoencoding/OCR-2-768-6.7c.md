# Plan — OCR-2 natif 768 (compression 6,7×)

## Objectif

Mesurer la PPL de continuation (objective `lm`) avec **DeepSeek-OCR-2 en résolution
native 768×768**, c'est-à-dire avec la grille causale **`query_768` (12×12 = 144
requêtes)** pré-entraînée, au lieu du `query_512` (8×8) interpolé du run 512.

But : lever le handicap « query interpolé hors distribution » et tester l'encodeur
DeepEncoder V2 dans sa configuration native. Ce run **n'est pas** une reproduction du
« tiny » du papier (budget différent) — voir la section Budget.

Branche : `ocr-2-native-768-6.7x`.

---

## Décisions validées

- **Images** : **re-render 768×768** (pas de downscale des `base` 1024).
- **Nom de mode / dossier** : `ocr2_768` → images dans `images/ocr2_768/{id}.png`.
- **Font size** : ~**15 px** (14–15), conséquence de la recherche binaire « faire tenir
  1000 tokens ». Pas de réglage manuel.
- **Encodeur gelé** (comme les autres runs), décodeur fine-tuné.

---

## Budget de tokens et compression

Chaîne : SAM `768/16/4 = 12×12` → **144 requêtes** + **1 `view_seperator`** =
**145 tokens image**. Dans la séquence : `1 BOS + 145 vision + 4 prompt ("Free OCR.")`
= **150 tokens de contexte effectifs**.

> Compression = `1000 / 150` = **6,67×** (convention du script, identique au 12,8× du
> papier qui compte 78 tokens = 73 vision + BOS + prompt).

| Config | Vision tokens | + BOS + prompt | Compression |
|---|---|---|---|
| OCR-1 tiny (papier) | 73 | 78 | 12,8× |
| OCR-2 512 (run actuel) | 64 + 1 = 65 | 70 | 14,3× |
| OCR-1 small | 111 | 116 | 8,6× |
| **OCR-2 768 (ce plan)** | **144 + 1 = 145** | **150** | **6,67×** |
| OCR-2 1024 (natif) | 256 + 1 = 257 | 262 | 3,8× |
| OCR-1 base | 273 | 278 | 3,6× |

**Conséquence** : 6,67× est ~2× moins agressif que le tiny du papier → PPL attendue
plus basse, **non comparable au 5,35**. À interpréter sur la courbe PPL-vs-compression.

## Font size (~15 px)

Le rendu adapte la police par recherche binaire entre 4 et 30 px. Les stats réelles
sur les modes existants :

| Résolution | font_size moyen |
|---|---|
| 512 | 9,9 px |
| 640 | 12,3 px |
| 1024 | 19,8 px |
| 1280 | 24,4 px |

Relation quasi linéaire (`font ≈ 0,0193 × R`) → **768 px ≈ 14,8 px, soit 14–15 px**
(fourchette ~11–25 px, ~38 lignes). Le `render_text_to_image` existant suffit.

## Étapes

### 0. Prérequis
- Run 512 en cours : ne pas y toucher (`outputs/vision_tiny_frozen_ocr2_lm`).
- Espace disque : ~**56 GB** pour 510k images 768 (~110 KB/image).
- Source du texte : champ `context_text` des Arrow (`train_arrow` / `val_arrow`) ou
  `samples.jsonl` (33 GB, dans `TODELETE-bad-autoencoding`).

### 1. Branche
```bash
git checkout -b ocr-2-native-768-6.7x
```

### 2. Re-render 768
- Script dédié (ex. `data/scripts/render_768.py`) qui :
  1. itère `train_arrow` + `val_arrow` (champ `context_text`, `id`) ;
  2. appelle `render_text_to_image(context_text, 768, 768)` (même fonction que
     `prepare_training_data.py`) ;
  3. sauvegarde `data/training/full/images/ocr2_768/{id}.png` (`optimize=True`) ;
  4. optionnel : écrit un `font_metadata_768.jsonl` (font_size, lines, is_truncated).
- Paralléliser (ProcessPoolExecutor, 16 workers). Durée estimée : quelques heures.
- **Ne pas** écraser `images/tiny` (512), partagé avec le run actuel.

### 3. Mode `ocr2_768`
- `trainers/config.py` :
  ```python
  VISION_MODES_OCR2['ocr2_768'] = {
      'base_size': 768, 'image_size': 768, 'tokens': 145, 'crop_mode': False,
  }
  ```
- `training/arguments.py` : ajouter `ocr2_768` aux `choices` de `--vision_mode`.
- Le dataset lit `images/{vision_mode}/{id}.png` → `images/ocr2_768/`. Les Arrow
  existants sont **réutilisables tels quels** (chemin dérivé de `sample_id`, pas du
  champ `images`).
- `query_512` : inoffensif ; optionnellement ne l'initialiser que pour le mode 512.

### 4. Smoke test (obligatoire avant le run complet)
- Charger le modèle (`ocr_version=ocr2`), trainer `vision_mode=ocr2_768`.
- Vérifier : **145 features** produites, `images_seq_mask` = 145 `True`,
  branche `query_768` sélectionnée (pas `query_512`), forward/backward OK.
- Vérifier qu'aucun padding n'est appliqué (image réellement 768×768).

### 5. Run complet
```bash
uv run python train.py \
  --regime vision --vision_mode ocr2_768 --ocr_version ocr2 --objective lm \
  --vision_prompt free_ocr --no-train-encoder \
  --data_path /shared/optizip-shared/bad-autoencoding/data/training/full/train_arrow \
  --val_data_path /shared/optizip-shared/bad-autoencoding/data/training/full/val_arrow \
  --output_dir outputs/vision_native768_ocr2_lm \
  --batch_size 8 --gradient_accumulation_steps 6 \
  --num_epochs 1 --learning_rate 1e-4 \
  --seed 42 --num_workers 8 --prefetch_factor 4 \
  --save_steps 0 --eval_steps 500 --initial_validation \
  --save_val_per_sample --num_qualitative_samples 0 \
  --attn_implementation eager
```
- Mêmes hyperparamètres que les runs OCR-1 tiny et OCR-2 512 (comparabilité).
- Durée : ~**4,5–5 jours** (144 requêtes au lieu de 64 → encodeur plus lourd ;
  séquence ~150 vs 70 tokens de contexte).

## Points à valider / risques

1. **Smoke test 145 features** (cf. étape 4) — bloquant.
2. **Re-render fidèle** : vérifier visuellement un échantillon 768 (police ~15 px,
   pas de troncature massive) et comparer au 512/1024.
3. **Collision de noms** : ne pas réutiliser `small` (640 px OCR-1) ; `ocr2_768` dédié.
4. **Baseline** : pas de mode OCR-1 à 145 tokens → comparer à la courbe du papier et
   encadrer par OCR-1 small (8,6×) / base (3,6×).
5. **Distribution** : « natif 768 » = grille native, mais l'entraînement OCR-2 utilisait
   des crops 768 + un global 1024 ; ce run est une page entière en 768. Caveat à noter.
6. **Coût** : ~4,5–5 jours ; vérifier l'espace disque (sorties ~40 GB + images ~56 GB).
7. **Repro** : seed 42, mêmes splits, même schedule (warmup 1041, total 10417 steps).
